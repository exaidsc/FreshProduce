## 一、数据库总体设计

### 1.1 数据库设计概述

本系统采用 MySQL 8.0 关系型数据库，数据库名为 `fresh_group_buy`，字符集采用 `utf8mb4` 以支持中文及emoji表情存储。数据库整体设计遵循关系型数据库三大范式，确保数据的原子性、完整性和一致性，同时通过合理的索引设计提升查询效率。

全库共设计 **10 张数据表**，分别为：用户表（user）、收货地址表（address）、商品分类表（category）、商品表（product）、团购活动表（group_activity）、订单主表（order）、订单明细表（order_item）、购物车表（cart）、团购参团记录表（group_join）、管理员表（admin）。

### 1.2 E-R 图设计

系统实体关系如下：

- **用户（user）** 与 **收货地址（address）**：一对多关系，一个用户可以拥有多个收货地址，每个地址仅属于一个用户
- **用户（user）** 与 **购物车（cart）**：一对多关系
- **用户（user）** 与 **订单（order）**：一对多关系
- **商品分类（category）** 与 **商品（product）**：一对多关系，一个分类下包含多个商品
- **商品（product）** 与 **团购活动（group_activity）**：一对多关系，一个商品可以发起多个团购活动
- **团购活动（group_activity）** 与 **团购参团记录（group_join）**：一对多关系
- **订单（order）** 与 **订单明细（order_item）**：一对多关系，一个订单包含多条商品明细
- **订单（order）** 与 **团购活动（group_activity）**：多对一关系，团购订单关联一个活动

### 1.4 三大范式设计说明

**第一范式（1NF）—— 字段原子性：**
所有字段均为不可再分的原子值。收货地址将省、市、区、详细地址拆分为独立字段，而非存储为一个完整地址字符串，满足字段原子性要求。

**第二范式（2NF）—— 消除部分依赖：**
所有表均使用单一主键（id），非主键字段完全依赖于主键，不存在部分依赖。订单商品信息独立为 order_item 明细表，通过 order_id 关联订单主表，避免了在订单表中冗余存储多条商品信息。

**第三范式（3NF）—— 消除传递依赖：**
商品分类信息独立为 category 表，商品表通过 category_id 外键关联，而非在商品表中存储分类名称等冗余字段。用户信息、地址信息均独立成表，订单通过外键关联，消除了传递依赖。

## 二、后端架构设计

### 2.1 技术选型

本系统后端采用 **Express.js** 框架开发，主要技术选型如下：

| 技术 | 版本 | 用途 | 选型理由 |
|------|------|------|----------|
| Node.js | 18+ | 运行环境 | 事件驱动、非阻塞I/O，适合高并发接口服务 |
| Express | 4.x | Web框架 | 轻量级、中间件生态丰富、开发效率高 |
| MySQL | 8.0 | 关系型数据库 | 课程要求、事务支持完善、关系建模清晰 |
| mysql2 | 3.x | 数据库驱动 | 支持Promise、连接池、预处理语句 |
| jsonwebtoken | 9.x | 身份认证 | 无状态Token认证，适合小程序前后端分离 |
| node-schedule | 2.x | 定时任务 | Cron表达式调度，实现团购自动成团 |
| axios | 1.x | HTTP客户端 | 调用微信登录接口换取openid |
| cors | 2.x | 跨域处理 | 支持小程序和Vue后台跨域访问 |

### 2.2 MVC 分层架构

后端采用经典的 MVC（Model-View-Controller）分层架构，结合 RESTful API 设计模式，整体分为以下几层：

```
┌─────────────────────────────────────────┐
│            客户端（小程序/Vue后台）        │
└──────────────────┬──────────────────────┘
                   │ HTTP请求
┌──────────────────▼──────────────────────┐
│              路由层 (Routes)              │
│     路径分发 → 中间件 → 控制器            │
└──────────────────┬──────────────────────┘
┌──────────────────▼──────────────────────┐
│            中间件层 (Middleware)          │
│  CORS跨域 │ JWT鉴权 │ 参数校验 │ 日志    │
└──────────────────┬──────────────────────┘
┌──────────────────▼──────────────────────┐
│            控制层 (Controller)            │
│  接收请求参数 │ 调用Service │ 返回响应     │
└──────────────────┬──────────────────────┘
┌──────────────────▼──────────────────────┐
│            业务层 (Service)               │
│  业务逻辑处理 │ 事务控制 │ 数据组装        │
└──────────────────┬──────────────────────┘
┌──────────────────▼──────────────────────┐
│            数据访问层 (Model/DB)          │
│  SQL执行 │ 连接池管理 │ 结果映射           │
└──────────────────┬──────────────────────┘
┌──────────────────▼──────────────────────┐
│              MySQL 数据库                 │
└─────────────────────────────────────────┘
```

**各层职责说明：**

- **路由层（Routes）**：统一注册所有API路径，将HTTP请求分发到对应控制器方法，同时配置中间件拦截规则
- **中间件层（Middleware）**：在请求到达控制器前进行预处理，包括跨域处理、身份认证、参数合法性校验、请求日志记录
- **控制层（Controller）**：接收并解析请求参数，调用对应的Service业务方法，将处理结果封装为统一格式返回
- **业务层（Service）**：核心业务逻辑处理，包括数据校验、事务控制、多表操作编排、业务规则实现
- **数据访问层（Model/DB）**：通过mysql2连接池执行SQL语句，管理数据库连接，返回查询结果

### 2.3 接口设计规范

### 2.4 权限校验机制

系统采用 **JWT（JSON Web Token）** 无状态身份认证机制，分为用户端和管理端两套鉴权体系：

#### （1）用户端鉴权流程

1. 用户通过微信登录接口（POST /api/user/login）提交 code
2. 后端调用微信接口换取 openid，查询或创建用户记录
3. 后端生成 JWT Token（payload 包含 userId、openid、nickname），返回给前端
4. 前端将 Token 存储在本地，后续请求在 Header 中携带 `Authorization: Bearer <token>`
5. 后端 authMiddleware 中间件解析并验证 Token，将用户信息挂载到 req.user 上
6. Token 有效期为7天，过期后需重新登录

#### （2）管理端鉴权流程

管理员通过账号密码登录后，生成包含 adminId、username、role 的 JWT Token，由 adminAuthMiddleware 中间件进行校验。管理后台接口统一使用 `/api/admin/` 前缀，均需通过管理员鉴权。

#### （3）鉴权中间件核心逻辑

- 从请求头 Authorization 字段提取 Token（去除 "Bearer " 前缀）
- 调用 jwt.verify() 验证签名和有效期
- 验证失败返回 401 未授权响应
- 验证成功将用户/管理员信息挂载到请求对象，传递给后续控制器

## 三、团购定时成团任务设计

### 3.1 业务背景与需求

团购活动的核心特征是"凑团"：用户发起或参与团购后，需要在规定时间内达到指定人数才能成团成功。如果活动截止时人数未达标，则团购失败，需要关闭活动并取消相关订单、回补商品库存。

这一过程不能依赖人工操作，必须通过**定时任务自动执行**，确保团购状态的及时更新和数据一致性。

### 3.2 定时任务整体设计

#### （1）调度策略

- **调度框架**：node-schedule
- **执行频率**：每分钟执行一次（Cron表达式：`0 * * * * *`）
- **启动时机**：服务启动后自动启动定时任务，并延迟3秒执行一次首轮扫描

#### （2）处理流程

```
开始
  │
  ▼
获取运行锁（isRunning）
  │
  ├─ 锁被占用 → 跳过本次执行（防止并发）
  │
  ▼
查询所有 status=1（进行中）的团购活动
  │
  ▼
逐个处理每个活动（串行执行，避免并发冲突）
  │
  ├─ 开启事务
  ├─ 行锁查询活动状态（SELECT ... FOR UPDATE）
  ├─ 统计实际参团人数（从 group_join 表 COUNT）
  │
  ├─ 人数 ≥ 成团人数？
  │   ├─ 是 → 【成团处理】
  │   │       1. 活动状态 → 已成团(2)
  │   │       2. 关联订单状态 → 待配送(2)
  │   │       3. 提交事务
  │   │
  │   └─ 否 → 活动已到期？
  │             ├─ 是 → 【未成团关闭处理】
  │             │       1. 活动状态 → 未成团关闭(3)
  │             │       2. 关联订单状态 → 已取消(5)
  │             │       3. 查询订单明细，回补商品库存
  │             │       4. 提交事务
  │             │
  │             └─ 否 → 跳过（未到期且未达标，等待下次扫描）
  │
  ▼
释放运行锁
  │
  ▼
结束
```

### 3.3 成团状态流转规则

| 活动状态 | 状态码 | 触发条件 | 关联订单状态变化 |
|----------|--------|----------|------------------|
| 进行中 | 1 | 创建活动时默认状态 | 订单：待成团(1) |
| 已成团 | 2 | 参团人数 ≥ min_people | 订单：待成团(1) → 待配送(2) |
| 未成团关闭 | 3 | 活动到期且人数未达标 | 订单：待成团(1) → 已取消(5)，库存回补 |
| 手动关闭 | 4 | 管理员手动关闭 | 订单不变（由管理员另行处理） |

### 3.4 容错机制设计

#### （1）事务保证数据一致性

成团处理和未成团关闭处理均使用数据库事务（BEGIN → COMMIT/ROLLBACK），确保活动状态更新、订单状态更新、库存回补等多步操作要么全部成功，要么全部回滚，避免出现数据不一致的中间状态。

#### （2）行锁防止并发处理

在处理单个活动前，使用 `SELECT ... FOR UPDATE` 对活动记录加行锁，防止在多实例部署或并发触发时同一活动被重复处理。

#### （3）运行锁防止重复执行

使用 `isRunning` 布尔变量作为任务级锁，当上一次执行尚未完成时，新的定时触发会直接跳过，避免任务堆积和重复处理。

#### （4）异常捕获与日志记录

每个活动的处理独立包裹 try-catch，单个活动处理失败不会影响其他活动的处理。所有关键操作（成团成功、未成团关闭、异常）均输出日志，包含活动ID、参团人数、耗时等信息，便于问题排查。

#### （5）实际人数统计不依赖冗余字段

参团人数通过实时查询 group_join 表统计（COUNT DISTINCT user_id），而非直接读取 group_activity 表的 current_people 字段，避免因并发写入导致的统计数据不准确。

### 3.5 库存回补逻辑

当团购活动因人数不足而关闭时，需要将已占用的商品库存回补：

1. 查询该活动下所有已取消订单的 order_item 明细
2. 按 product_id 分组汇总购买数量（SUM(quantity)）
3. 逐个商品执行 `UPDATE product SET stock = stock + 回补数量 WHERE id = ?`
4. 整个回补过程在同一事务中，与活动关闭、订单取消原子提交
